# Phase 2.1 Calibration Design (Evidence + Severity)

## 1) Phase 2.0 Findings

Phase 2.0 (25 scenario-category records; 5 scenarios x 5 categories) established a clear baseline:

- Finding alignment: 25/25 STRONG (100%)
- Engineering usefulness: 23/25 HIGH (92%)
- Evidence discipline: 9/25 GROUNDED (36%), 16/25 MIXED (64%), 0/25 UNSUPPORTED
- Category relevance: 19/25 FOCUSED (76%), 6/25 SOME_LEAKAGE (24%)
- Severity calibration: 1/25 CALIBRATED (4%), 18/25 ONE_LEVEL_OFF (72%), 6/25 MATERIALLY_MISALIGNED (24%)
- Overall judgment: 19/25 STRONG (76%), 6/25 MIXED (24%)

Observed pattern across adjudication notes and raw LLM outputs:

- The model consistently identifies relevant engineering concerns and proposes actionable mitigations.
- Many findings are phrased from absent details ("not specified", "no explicit X"), then scored as if the control is confirmed missing.
- Because severity is derived from score, score inflation creates severity inflation (predominantly HIGH / CRITICAL).
- Category leakage appears most often in Cost and Observability when risks expand into broader reliability/security framing.

## 2) Root-Cause Hypothesis

The calibration issue is most likely generated by the interaction of three current design choices:

1. **Prompt gap in evidence taxonomy**
   - Current reviewer system instructions ask for category-focused risks but do not require explicit evidence labels (`OBSERVED`, `NOT_SPECIFIED`, `INFERRED_RISK`).
   - Result: "not specified" evidence is often treated as confirmed deficiency in wording and scoring.

2. **Single scalar control variable (`score`) drives severity**
   - Current schemas accept only `score` + free-text reasoning/risk fields.
   - `CategoryReview.severity` is derived deterministically from score (`derive_severity(...)`), so any score inflation directly becomes severity inflation.

3. **No explicit severity decision rubric in prompt**
   - Current prompts define score bands, but do not operationalize severity by evidence strength, blast radius, likelihood, compensating controls, and confirmed-vs-inferred status.
   - The model defaults to risk-forward "defensive pessimism," especially when architecture details are sparse.

Where this can be addressed with minimal intervention:

- `backend/app/reviewers/security_llm.py`
- `backend/app/reviewers/scalability_llm.py`
- `backend/app/reviewers/reliability_llm.py`
- `backend/app/reviewers/observability_llm.py`
- `backend/app/reviewers/cost_llm.py`
- `backend/app/schemas/review.py` (only for the structured-field alternative)
- `backend/app/reviewers/llm_shared.py` (mapping structured fields to existing output, if schema extended)

## 3) Proposed Intervention

Introduce calibration guardrails at prompt/schema boundary (not model change, no second-pass LLM, no post-hoc heuristic ranker).

Core policy to add:

- Every material risk statement must declare one evidence basis:
  - `OBSERVED`: directly supported by provided architecture fields.
  - `NOT_SPECIFIED`: architecture lacks enough information to determine control presence/quality.
  - `INFERRED_RISK`: plausible production risk inferred from explicit architecture characteristics.
- The reviewer must not silently convert `NOT_SPECIFIED` into "missing/not implemented."
- Severity/score must be justified by:
  - evidence strength,
  - likelihood,
  - blast radius,
  - production impact,
  - compensating controls,
  - confirmed vs inferred status.
- Enforce category discipline statement:
  - analyze only assigned category;
  - cross-category mention allowed only when causally necessary for assigned category's outcome.

## 4) Prompt / Schema Changes To Make

This section defines the intended Phase 2.1 change set (design only; not implemented here).

### 4.1 Common prompt module (new shared calibration block)

Create a reusable "Calibration Addendum" string used by all 5 LLM reviewers, appended to existing category-specific prompts.

Required content:

1. **Evidence taxonomy**
   - Define `OBSERVED`, `NOT_SPECIFIED`, `INFERRED_RISK` exactly.
   - Explicit rule: if `NOT_SPECIFIED`, phrase as uncertainty and validation need; do not assert absence.

2. **Severity rubric**
   - `LOW`: limited impact or speculative concern; low likelihood; narrow blast radius; clear compensating controls.
   - `MEDIUM`: credible risk requiring planned mitigation, but not immediate launch blocker; impact bounded or partially mitigated.
   - `HIGH`: strong evidence of meaningful production risk with realistic trigger conditions and material impact; controls missing/weak with limited compensation.
   - `CRITICAL`: confirmed or near-certain severe risk with high blast radius and unacceptable production impact; typically release blocker.

3. **Calibration constraints**
   - `NOT_SPECIFIED` alone should generally cap at MEDIUM unless explicit architecture signals justify higher risk by compounding factors.
   - `HIGH`/`CRITICAL` should require explicit rationale tying likelihood + blast radius + weak/absent compensating controls.
   - Prefer specific, testable recommendations over generalized hardening lists.

4. **Category boundary clause**
   - Mention adjacent category concerns only if direct causal effect on assigned category.
   - If mentioned, keep to one concise line and return to assigned category.

### 4.2 Reviewer prompt updates (all five reviewers)

For each reviewer file (`*_llm.py`):

- Preserve current category-specific domain bullets.
- Append the shared calibration addendum.
- Add one short category-specific boundary reminder:
  - Security: do not absorb pure cost/observability concerns unless they materially alter exploitability/detection.
  - Scalability: avoid pure reliability judgments unless directly affecting scale behavior.
  - Reliability: avoid cost optimization framing unless directly impacting failure containment/recovery.
  - Observability: avoid broad security/reliability scoring unless visibility gap directly impairs diagnosability.
  - Cost: avoid converting operational/monitoring concerns into security/reliability findings unless they directly drive cost risk.

### 4.3 Structured output enhancement (alternative 2 only)

Extend each `*ReviewerLLMResult` schema in `backend/app/schemas/review.py`:

- Replace free-form `risks: list[str]` with structured `findings: list[LLMFinding]` where:
  - `statement: str`
  - `evidence_basis: EvidenceBasis` (`OBSERVED | NOT_SPECIFIED | INFERRED_RISK`)
  - `severity_hint: Severity` (finding-level, model-provided)
  - `confidence: int (0-100)` (optional but useful)
  - `category_relevance_note: str` (optional short rationale when cross-category reference exists)

And add top-level rationale fields:

- `score_rationale: str` (why overall score aligns with evidence mix)
- `severity_rationale: str` (why aggregate severity band is justified)

Compatibility mapping:

- `run_llm_category_review(...)` maps `findings[].statement` into `CategoryReview.issues` to preserve existing API contract.
- keep deterministic `derive_vote(...)` unchanged.
- for minimal churn, keep aggregate severity derived from score in Phase 2.1; use `severity_hint` for analysis only (not runtime behavior change) during A/B.

## 5) Alternatives Considered

## Alternative A — Prompt-Only Calibration

### Description

Add evidence taxonomy + severity calibration rules directly into existing 5 prompts; no schema changes.

### Pros

- Lowest implementation complexity.
- Minimal test impact and no contract migration.
- Cleanest "single-variable" A/B vs Phase 2.0 (prompt text only).

### Cons

- Weak observability: evaluation cannot directly measure per-finding evidence basis from model output.
- Harder to diagnose whether calibration improved due to explicit evidence discipline vs incidental wording shifts.
- Relies entirely on instruction-following in free text.

## Alternative B — Prompt + Structured Evidence/Severity Fields

### Description

Add calibration prompt guidance and require structured per-finding evidence/severity metadata in reviewer schema outputs.

### Pros

- Strong observability and evaluability:
  - direct per-finding evidence basis distribution,
  - explicit comparison of inferred vs observed risk severity.
- Easier adjudication quality control (human reviewers inspect explicit evidence tags).
- Better long-term foundation for moderator/synthesis and future automated diagnostics.

### Cons

- Moderate implementation complexity (schema + mapping + tests).
- Higher behavior shift risk due to output format changes.
- Slightly noisier A/B interpretation because both prompt and schema constraints change together.

## 6) Recommended Approach

Recommend **Alternative B (Prompt + Structured Evidence/Severity Fields)** with a phased rollout:

1. Phase 2.1a (internal): implement prompt + schema changes together, preserve final `CategoryReview` contract.
2. Run controlled evaluation against the same dataset/rubric.
3. If alignment/usefulness regresses materially, fallback to prompt-only variant quickly (rollback section below).

Why this recommendation:

- The core Phase 2.0 weakness is not finding quality but calibration transparency.
- Structured evidence fields create direct instrumentation of the failure mode we are trying to correct.
- This improves confidence in whether gains are real and durable, while still keeping runtime behavior and model constant.

## 7) Experimental Controls (Phase 2.1 vs Phase 2.0)

Keep constant:

- same 5 scenarios,
- same 5 categories,
- same reference dataset fixture,
- same model/provider configuration,
- same evaluation runner flow,
- same human adjudication rubric dimensions.

Change only:

- reviewer calibration intervention (prompt and, in recommended approach, reviewer output schema fields for evidence/severity annotation).

A/B setup:

- **A (baseline):** Phase 2.0 reviewer prompts/schemas.
- **B (treatment):** Phase 2.1 calibration prompts + structured finding metadata.

Adjudication process:

- Continue single-record human adjudication using existing rubric.
- Add a lightweight supplemental readout for treatment run:
  - evidence basis distribution in generated findings,
  - severity by evidence basis (especially `NOT_SPECIFIED` findings).

## 8) Success Criteria

Primary goals (must improve):

- Evidence discipline:
  - increase GROUNDED from 36% to >= 60%;
  - keep UNSUPPORTED at 0%.
- Severity calibration:
  - increase CALIBRATED from 4% to >= 35%;
  - reduce MATERIALLY_MISALIGNED from 24% to <= 10%.
- Category relevance:
  - increase FOCUSED from 76% to >= 88%;
  - reduce SOME_LEAKAGE from 24% to <= 12%.

Preservation goals (must not regress materially):

- Finding alignment remains >= 92% STRONG.
- Engineering usefulness remains >= 88% HIGH.
- No trend toward generic/non-actionable recommendations.

## 9) Risks / Tradeoffs

1. **Over-correction risk (too conservative)**
   - Strong guardrails may suppress legitimate HIGH/CRITICAL inferred risks.
   - Mitigation: explicit allowance for high-severity inferred risks when compounding factors and blast radius are clearly justified.

2. **Verbosity / schema burden**
   - Structured finding metadata can reduce fluency and increase output overhead.
   - Mitigation: cap number of findings; concise rationale fields.

3. **Cross-category underreporting**
   - Boundary discipline may hide valid cross-dimensional interactions.
   - Mitigation: allow bounded cross-category mention only with direct causal tie.

4. **A/B interpretability complexity**
   - Prompt + schema change together introduces two moving parts.
   - Mitigation: maintain a prompt-only fallback branch for quick confirmatory run if needed.

## 10) Rollback Plan

If Phase 2.1 treatment degrades alignment/usefulness or introduces excessive conservatism:

1. Revert to Phase 2.0 prompt strings and prior reviewer output schema.
2. Keep the experiment harness, dataset, and adjudication rubric unchanged.
3. Execute prompt-only calibration variant as a narrower fallback intervention.
4. Compare against baseline with the same adjudication process before promoting any calibration change.

Rollback trigger thresholds:

- Finding alignment drops below 92% STRONG, or
- Engineering usefulness drops below 88% HIGH, or
- Qualitative adjudication indicates generic/vague recommendations trend.

### 11.4 Phase 2.2 current hypothesis and implementation

Current Phase 2.2 hypothesis:

> Explicitly separating observed evidence, unspecified information, and inferred risk at the finding level will improve evidence discipline without sacrificing the severity-calibration gains achieved in Phase 2.1.

Intended distinction:
- `OBSERVED`: directly supported by provided evidence.
- `NOT_SPECIFIED`: provided material does not establish whether the control/detail exists.
- `INFERRED_RISK`: conditional risk derived from available evidence or an unspecified condition.

Principle:

> Unknown != absent != risky.

Current implementation is intentionally minimal and prompt-only:
- Changed file: `backend/app/reviewers/llm_shared.py`
- Changed section: `_CALIBRATION_ADDENDUM`
- Strengthened rules to prevent unspecified details from being phrased as established deficiencies, while preserving conditional inference guidance and Phase 2.1 severity-calibration scaffolding.

No redesign was made to:
- schema,
- validator architecture,
- provider/model configuration,
- runner/evaluation protocol,
- rubric/adjudication criteria.

### 11.5 Phase 2.2 validation progression and preflight gate

Phase 2.2 validation evolved in controlled steps:

- Initial prompt-only intervention checks passed in focused/local tests.
- Follow-on live checks exposed validator robustness gaps around semantically valid `NOT_SPECIFIED` wording.
- Validator hardening updates were applied to preserve contract intent while reducing wording false positives:
  - removed brittle positive uncertainty-whitelist enforcement as a mandatory gate,
  - retained asserted-absence contradiction checks,
  - retained mixed-basis (`NOT_SPECIFIED` + inferred consequence) rejection,
  - refined asserted-absence patterning so "there is no information/specification/detail/mention of X" is treated as `NOT_SPECIFIED` rather than proven absence,
  - removed `single points of failure` as a lexical inferred-impact marker in mixed-claim detection because it can describe the purpose/target of a missing control, not only a consequence assertion.
- Shared calibration prompt was minimally clarified to operationalize split behavior:
  - consequence clauses (e.g., "which could", "creating", "leading to", "resulting in", "causing") must not appear inside `NOT_SPECIFIED` findings,
  - start a separate `INFERRED_RISK` finding instead,
  - include one concrete split example.
